## Overview

LearningMAP is a full-stack tutoring demo. The frontend is a set of static pages; the backend is a FastAPI service built on a **LangGraph** state machine. Every HTTP request drives one single-round graph execution; branches are selected by an `intent` node:

```
intent ──► chat
       ├─► knowledge_graph
       ├─► quiz
       ├─► grading ──► diagnosis ──► lesson
       └─► slides   (outline → per-page content + layout)
```

This branch plugs an independent **learning memory subservice** (`student_memory/`) on top of the base demo, providing cross-session semantic retrieval and L2 reflection notes. Session state is persisted in memory and SQLite.

The system **does not ingest user-uploaded documents** — content is generated by the LLM from the topic itself, then optionally grounded against the cross-session memory store.

## Key Features

### 📚 Learning Content Pipeline

A linear loop converts a topic into multi-format study materials:

- **Knowledge Graph** — entity/skill graph with mastery annotations (`mastery_annotator.py`).
- **Adaptive Quiz** — questions calibrated to the current KG mastery state.
- **Grading & Diagnosis** — per-question grading feeds a diagnosis card and a learning radar chart.
- **Markdown Lesson** — targeted to the weak points exposed by diagnosis; streamed via SSE.
- **Slide Deck** — outline-first pipeline, exported to `.pptx` via `python-pptx`. The post-processing chain enforces a 1000 × 562.5 canvas, repairs LaTeX/CJK elements, and assigns stable IDs (see [Architecture](#architecture)).

### 🧠 Persistent Memory

An independent FastAPI microservice (`student_memory/`) provides:

- `POST /retrieve` — semantic recall injected into the chat node's system prompt.
- `POST /ingest` — sub-topic-level MemoryUnits written at end of diagnosis / lesson.
- `POST /notes` and `GET /notes/{uid}/neighbors` — 4-category L2 reflection notes for wrong-answer review.

The seam is a single file, `src/memory_client.py`. **When the service is unavailable, the main service degrades gracefully** — no context injection, no ingest writes, no blocking.

### 🎓 Pluggable Pedagogy Skills

Teaching style is a swappable artifact, not code:

- Each pedagogy is a directory containing one `SKILL.md` (e.g. `skills/feynman/`, `skills/scaffolding/`, `skills/socratic/`).
- Adding a new pedagogy is **one new directory + one `SKILL.md` — zero Python changes**.
- A separate **KC-skill bank** (built offline via `run/build_kc_skills.py`) is resolved per topic by `kc_skill_resolver.py`, allowing skill injections to be scoped to specific knowledge components.
- Skills are toggled at runtime via `POST /api/chat/{sid}/set-skill`.

### 🔁 Review Loop (L2 Reflection)

After the main learning loop, the review node:

- Generates 4-category wrong-answer summaries.
- Persists them to `student_memory` via `/notes`.
- Subsequent sessions surface these notes through `/retrieve`, closing the cross-session feedback loop.

The minimum gap between review runs is bounded by `REVIEW_MIN_AGE_SECONDS` (default 24 h).

## Architecture

### Pipeline Diagram

```
User enters a topic
      │
      ▼
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ knowledge_   │──►│ Adaptive Quiz│──►│  Grading +   │
│  graph node  │   │  (quiz node) │   │  Diagnosis   │
└──────────────┘   └──────────────┘   └──────┬───────┘
                                             │
                       ┌─────────────────────┴───────────────┐
                       ▼                                     ▼
                ┌──────────────┐                      ┌──────────────┐
                │ Markdown     │                      │  PPT Slides  │
                │ Lesson       │                      │ (slides node)│
                │ (lesson node)│                      │              │
                └──────────────┘                      └──────────────┘
                       │                                     │
                       └─────────────┬───────────────────────┘
                                     ▼
                       Review node (recap / L2 notes)
                                     │
                                     ▼
               POST /ingest + /notes  →  student_memory
                                     │
              next session's chat node  ◄── POST /retrieve
```

### LangGraph State Machine

- Single-round per HTTP request, assembled in `src/agent/graph.py`.
- `LearningState` (Pydantic) carries the full execution context across nodes.
- The `chat` node injects historical memory snapshots as a system-prompt augmentation and safely degrades when the store is empty.

### Slide Post-Processing Chain

Brittle LLM JSON is normalized through a fixed chain — **do not** add ad-hoc fixes inside individual nodes:

```
LLM JSON
   │
   ▼
parse_json_response  →  _fix_element_defaults
                              │
                              ▼
                      _process_latex_elements  (CJK → TextElement)
                              │
                              ▼
                      _enforce_canvas_bounds   (1000 × 562.5)
                              │
                              ▼
                      _assign_ids_and_rotation
                              │
                              ▼
                          Pydantic validation
```

JSON repair itself is centralized in `src/utils/json_repair.py` (4-strategy).

### Memory & Knowledge Layer

- **Vector store**: `student_memory/` uses hnswlib HNSW with BAAI/bge-m3 (default) or bge-small-zh-v1.5 embeddings.
- **Session store**: in-memory dict + SQLite (`sessions.db`) dual-write, exposed via `GET /api/chat/{sid}/state` for full frontend reconstruction.
- **Forgetting curve**: `src/forgetting/` implements an Ebbinghaus-style decay used by the review trigger.

### LLM Layer

- **Provider**: OpenAI-compatible gateway only (DeepSeek / Moonshot / any OpenAI-compatible API). No multi-provider abstraction, no tool-use loop.
- **Structured output**: Instructor on top of the OpenAI SDK; schemas in `src/llm/schemas.py` and `src/llm/slide_schemas.py`.
- **Async discipline**: every LLM call goes through `src/llm/client.py`, wrapped in `asyncio.to_thread` so the event loop is never blocked.
- **Prompts**: all live in `src/prompts/*.j2` as Jinja2 templates. Never inline a prompt string in a Python module. `slide_content_system.j2` (~961 lines) is load-bearing.

## Capabilities Summary

- **Adaptive learning loop** — topic → KG → quiz → grading → diagnosis → targeted lesson, all derivable from session state on refresh.
- **Slide generation** — Markdown lessons re-rendered as 16:9 slide decks (1000 × 562.5 canvas), with LaTeX/CJK aware post-processing and `.pptx` export.
- **Cross-session memory** — prior sessions resurface as system-prompt augmentations, decoupled behind a single seam and degraded gracefully when offline.
- **Pluggable pedagogy** — switch teaching style at runtime without redeploying; new pedagogies are plain directories.
- **Streaming everywhere** — chat, lesson, and slides ship over SSE.

## Installation

### Prerequisites

| Dependency | Version | Notes |
|---|---|---|
| Python | 3.11 | Locked by `.python-version` |
| [uv](https://docs.astral.sh/uv/) | 0.4+ | Only supported package manager |
| SQLite | 3.35+ | Bundled with Python |
| OpenAI-compatible LLM | — | DeepSeek / Moonshot / any OpenAI-compatible gateway |

### Local

```bash
uv sync                                # main service
cd student_memory && uv sync && cd ..  # memory subservice (optional)
```

### Running

**Main service (port 8080)**

```bash
uv run python run/serve.py
# Uvicorn → http://0.0.0.0:8080
```

**Memory subservice (port 8090, optional)**

```bash
cd student_memory
SM_USE_FAKE_EMBEDDER=1 uv run uvicorn app.main:app --host 127.0.0.1 --port 8090
```

> When the memory service is unavailable, the main service **gracefully degrades** (no `context_text` injection, no `ingest` writes) without blocking the conversation.

Open `http://localhost:8080/` once the main service is running — FastAPI serves `static/` from the root.

## Configuration

All variables read by the main service (set in `.env` or process environment):

| Variable | Default | Purpose |
|---|---|---|
| `OPENAI_API_KEY` | — | **Required**. LLM authentication. |
| `OPENAI_BASE_URL` | — | **Required**. OpenAI-compatible endpoint. |
| `LLM_MODEL` | — | **Required**. Model name. |
| `MEMORY_SERVICE_URL` | `http://127.0.0.1:8090` | `student_memory` service address. |
| `ALLOWED_ORIGINS` | `*` | Comma-separated CORS whitelist. |
| `REVIEW_MIN_AGE_SECONDS` | `86400` | Minimum interval between review-node invocations (seconds). |
| `CLASSBA_AUTH` / `CLASSBA_API_URL` / `CLASSBA_AGENT_NAME` | — | Optional. For ClassBA external Agent calls. |

The LLM client is hardcoded to **bypass the OS HTTP proxy** (see commit `fc7e51c`); no additional proxy configuration is needed.

Example `.env`:

```bash
OPENAI_API_KEY=sk-xxxxxxxx
OPENAI_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat

# Optional — defaults are used if omitted
MEMORY_SERVICE_URL=http://127.0.0.1:8090
ALLOWED_ORIGINS=*
REVIEW_MIN_AGE_SECONDS=86400
```

## API Reference

All routes are mounted under `/api` (see `src/api/chat.py` for the full list):

| Method | Path | Description |
|---|---|---|
| POST | `/api/chat` | Single-round chat (synchronous) |
| POST | `/api/chat/stream` | Single-round chat (SSE streaming) |
| POST | `/api/chat/{sid}/generate-quiz/stream` | Generate adaptive quiz |
| POST | `/api/chat/{sid}/submit-quiz` | Submit answers → grading → diagnosis |
| POST | `/api/chat/{sid}/generate-lesson` | Generate Markdown lesson |
| POST | `/api/chat/{sid}/generate-lesson/stream` | Same, streamed via SSE |
| POST | `/api/chat/{sid}/generate-slides` | Generate slides |
| POST | `/api/chat/{sid}/generate-slides/stream` | Same, streamed via SSE |
| GET  | `/api/chat/{sid}/export-pptx` | Export `.pptx` file |
| GET  | `/api/chat/{sid}/state` | Fetch full session snapshot (for frontend reconstruction) |
| POST | `/api/chat/{sid}/generate/{task_type}` | Generic background-task dispatcher |
| GET  | `/api/chat/{sid}/generate/{task_type}/status` | Get task status |
| POST | `/api/chat/{sid}/generate/{task_type}/cancel` | Cancel a task |
| GET  | `/api/skills` | List pedagogy skills |
| POST | `/api/chat/{sid}/set-skill` | Switch the active skill |
| POST | `/api/chat/{sid}/toggle-knowledge-skills` | Toggle KS injection |
| POST | `/api/chat/{sid}/toggle-kc-skills` | Toggle KC-skill injection |
| POST | `/api/chat/{sid}/start-review` | Start the L2 review flow |
| POST | `/api/chat/{sid}/submit-review` | Submit review results |
| GET  | `/health` | Health check |

> The frontend uses `GET /api/chat/{sid}/state` to **fully reconstruct** the session view (charts, diagnosis cards, lesson buttons). Any view element that must survive a page refresh **must be derivable from `state`** — relying on the message stream alone is not enough.

## Hardware Recommendations

The main service itself **does not run models locally** (inference is offloaded to an external LLM gateway). Machine load comes mostly from `student_memory`'s local embedding model.

### Main service only (external LLM, memory subservice disabled)

| Resource | Recommended | Minimum |
|---|---|---|
| CPU | 4 cores | 2 cores |
| Memory | 4 GB | 2 GB |
| Disk | 2 GB (deps + `sessions.db`) | 1 GB |
| GPU | Not required | Not required |
| Network | Reachable `OPENAI_BASE_URL`; lower latency = faster responses | — |

> What really determines the user experience is **the LLM gateway's latency and concurrency quota**, not local machine performance. The time-to-first-token of the streaming endpoints (`/chat/stream` etc.) is essentially the gateway's TTFT.

### Memory subservice enabled (with local vector embeddings)

The memory service runs all embedding inference locally; hardware requirements depend on the embedder you pick:

| Embedder | `SM_EMBEDDING_MODEL` | Dim | RAM | Disk | GPU |
|---|---|---|---|---|---|
| **FakeEmbedder** (dev/demo) | `fake-test` | 16 | < 100 MB | < 10 MB | Not required |
| **bge-small-zh-v1.5** (lightweight) | `BAAI/bge-small-zh-v1.5` | 512 | ~1 GB | ~500 MB | Optional (CPU works) |
| **bge-m3** (default, multilingual) | `BAAI/bge-m3` | 1024 | ~3 GB | ~2.5 GB | Recommended |

Recommended sizing when the main service and the memory service share a single host:

| Profile | CPU | RAM | Disk | GPU |
|---|---|---|---|---|
| Dev / demo (FakeEmbedder) | 4 cores | 4 GB | 2 GB | None |
| Single-host prod · bge-small-zh, CPU only | 8 cores | 6 GB | 4 GB | None |
| Single-host prod · bge-m3, CPU | 8 cores | 8 GB | 6 GB | None (slightly slower) |
| Single-host prod · bge-m3, GPU-accelerated | 4 cores | 8 GB | 6 GB | ≥ 6 GB VRAM (e.g. RTX 3060 / T4) |

Practical notes:

- **First start downloads the model**: bge-m3 ≈ 2 GB, bge-small-zh ≈ 500 MB. Warm up beforehand or use a proxy.
- **GPU is not strictly required** for bge-m3, but a single `/retrieve` inference on CPU takes ~200–500 ms; for high-concurrency scenarios switch to bge-small-zh or add a GPU.
- **Mac Apple Silicon (M1/M2/M3)** can use `SM_EMBEDDING_DEVICE=mps` for Metal acceleration; on 8 GB unified-memory models, prefer bge-small-zh.
- **Single-worker only**: the memory service's hnswlib index is not process-safe. **Run a single worker** and rely on thread-level concurrency.

## Testing & Development Conventions

```bash
# Main project
uv run python -m pytest tests/ -v
uv run python -m pytest tests/test_api.py::test_name -v   # single test

# Memory subproject
cd student_memory && uv run pytest -v
```

Lint / format:

```bash
uv run ruff check src/ run/ tests/
uv run ruff format src/ run/ tests/
```

Conventions:

- **Package management**: `uv` only; do not mix in pip / poetry.
- **LLM calls**: always through `src/llm/client.py`, always wrapped in `asyncio.to_thread`.
- **Prompt edits**: only inside `.j2` files; never concatenate prompt strings in Python.
- **Replayable state**: any visual element the frontend needs to restore after a refresh must be derivable from `GET /api/chat/{sid}/state`.
- **Extending `PPTElement`**: when adding a new type, update all 5 sites — `slide_schemas.py`, the slide post-processing chain, the `slides.html` renderer, `pptx_export.py`, and `slide_content_system.j2`.
- **XSS**: every frontend `innerHTML` write must go through `escapeHtml` or DOMPurify first.
- **Tests under `tests/manual/`** are smoke scripts; pytest skips them via `norecursedirs` by default.
- **One-shot regression scripts** should be `rm`'d after running — do not `git add` them.
